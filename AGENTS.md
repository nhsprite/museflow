# MuseFlow — Agent Context

AI Native 长篇小说生成 CLI 工具 (AI-native long-form novel generation CLI). A locally-run Node.js tool: enter a one-sentence story pitch and AI handles worldbuilding, outline generation, and chapter-by-chapter drafting. LangGraph orchestrates 10 specialized agents; all state lives in local JSON + filesystem storage — no database.

- **Stack**: Node.js >= 20, TypeScript (strict, ESM), LangGraph (`@langchain/langgraph`), Commander, zod, Inquirer, Vitest.
- **Distribution**: published to npm as `museflow` (`bin: museflow -> dist/cli/index.js`).

## Storage Architecture (Critical)

**MuseFlow uses JSON + filesystem storage only. It does NOT use SQLite.** Do not add SQLite migrations or SQL queries.

- **Config**: `museflow config set` writes project-level `./.museflow/config.json`, which takes precedence over the optional global fallback `~/.museflow/config.json` (see `src/config/store.ts`). Provider values `minimax`/`local` are normalized to `openai` (OpenAI-compatible endpoints).
- **Story directory**: `books/{title-slug}-{shortId}/` (title + id suffix, not the raw story id).
- **Checkpoints**: `books/{story-dir}/checkpoints/*.json` — LangGraph checkpoint JSON written by the custom `JsonCheckpointer` (`src/graph/checkpointer.ts`); `latest.json` points to the newest. **Checkpoints are the runtime source of truth.**
- **Projections/artifacts (regenerated by code)**: `meta.json` (CLI display), `outline.md`, `story_bible.md`, `chapters/chapter_{n}.md`, `reports/chapter_{n}.report.json`, `reports/blocking_*.json`, `output/*.txt` exports.
- **Debug logs**: `--debug` flag (or `MUSEFLOW_DEBUG=1`) wraps the model provider and appends LLM sessions to `.museflow/debug/sessions.jsonl`.

## Runtime Architecture

- **Graph**: `src/graph/novel.graph.ts` owns the LangGraph state machine. Story creation path: `build_world → create_characters → create_outline → validate_outline → finalize_story`. Chapter loop: `prepare_chapter → converge_and_decide → draft_chapter|fix_chapter|repair_state → validate_chapter_structured → validate_chapter_comprehensive → converge_and_decide → finalize_chapter|request_rewrite`. `request_rewrite` ends the graph with a blocking report for manual resolution.
- **Checkpoint is the source of truth**: `meta.json` and the other files are projections for CLI display and external inspection, exported from the persisted checkpoint. Malformed checkpoint JSON, invalid latest pointers, and corrupted chapter markers raise `CheckpointCorruptionError` with recovery guidance; never silently treat them as empty state.
- **Chapter commit boundary**: after `graph.invoke()` returns, `src/core/chapter-commit.ts` saves the finalized chapter marker from the persisted checkpoint and exports the `meta.json` projection. `.staging/chapter-commit.json` journals `prepared → content_promoted → marker_saved`; startup reconciliation verifies the journalled content hash, replaces stale rewrite content from staging, restores missing content/markers, and finishes journalled rewrite truncation before clearing the journal. Do not duplicate that marker/export sequence in command code.
- **Prose hygiene gate**: `src/graph/services/prose-hygiene/` is the shared deterministic prose-sanitization module (`checkProseHygiene` + `sanitizeProseExcerpt`). Detection is restricted to machine-readable formats (protocol `===` markers, event lines, final-state JSON) and known-identifier set membership (entity/beat ids, valid chapter numbers) — never NL matching. Error-severity codes: `prose.protocol-block`, `prose.internal-identifier`, `prose.chapter-self-reference` (`prose.meta-narration` is reserved for the advisory lane, `consistency.prose-artifact`; checklist re-recitation/repetition findings use the sibling stable code `consistency.prose-repetition` via the consistency agent's `prose_repetition` aspect, so routing fingerprints apply). It is wired at `ChapterAgent.parse` (parse failure → draft retry loop with `draft.prose-hygiene` feedback), `validateFixedChapterContent` (draft/fix output validation), the commit boundary (`assertStagedChapterHygiene` dry-run before `promoteStagedChapterContent`; failure aborts the commit with a `prose_hygiene` blocking report), and the previous-chapter-ending re-feed (`chapter-window.ts` sanitizes before prompt injection). Historical chapters are repaired via `scripts/repair-chapter-prose.ts` (mechanically removable residue only; the rest is reported).
- **JIT outline expansion**: `src/core/outline-expander.ts` generates a chapter outline and `ChapterPlan` immediately before drafting, using story arc progress, prior summaries, story state, pending tasks, and next-chapter boundary hints. Claimed mandatory/key beats are semantically verified against the outline description before drafting (`src/graph/services/plot-advance/beat-claim-verifier.ts`); unrealized claims are retried with a `beatClaimRejection` feedback section, then stripped after retry exhaustion (warning issue `outline.beat-claim-stripped`). Act-boundary pressure is injected at the outline stage as well (not only planning) in two tiers: pacing (medium) pressure fires when pending beats exceed the every-other-chapter pace (`pending * 2 > chapters left including current`), forcing a claim with the same rejection/retry loop but allowing a beatless soft landing with a warning issue (`outline.zero-claim-under-pacing-pressure`) after retry exhaustion; under high pressure (pending mandatory beats > chapters left after the current one) the outline prompt closes its zero-progress escape hatch (via `mandatoryBeatClaimRequired`), a zero-claim outline is rejected and retried with a `requiredClaims` feedback section, and on retry exhaustion the chapter aborts with a manual-resolution error instead of finalizing a beatless outline. The same high-pressure rule covers the claim-stripping path: if stripping unrealized claims would leave the outline with zero mandatory-beat claims, the chapter aborts as well rather than slipping through beatless. Independent of beat arithmetic, after `zeroClaimEscalationThreshold` (default 2) consecutive zero-claim chapters (tracked in graph-state `consecutiveZeroClaimChapters`, updated at finalization; only counts chapters whose act still has claimable beats) the outline stage closes the zero-claim escape hatch as well: zero-claim outlines are rejected/retried with `requiredClaims` (`pressureSource: 'zero_claim_streak'`) and retry exhaustion aborts the chapter — no pacing-style soft landing. Plan density validation (`validateChapterPlanBudget`) treats empty `sections` or zero total word count as invalid and retries with feedback instead of passing silently.
- **Routing**: `src/core/chapter-generation/routing/` decides whether to draft, patch-fix, repair state, finalize, or stop for manual rewrite, using issue fingerprints for stall detection. When the same beat stays `beat_unproven` for consecutive rounds, routing treats it as an outline-level false claim: it revokes the claim from the persisted outline (`beat-claim-revocation.ts`) and discards the plan for rebuild instead of re-drafting forever; the beat stays pending for later chapters. Exception: under act-boundary high pressure (pending mandatory beats > chapters left in the act), revoking a _mandatory_ beat claim is blocked (revoking would finalize the chapter consuming nothing). Instead, routing feeds the prose-stage rejection back into outline generation (`outline-regeneration.ts`): the chapter outline is force-regenerated with a `BeatClaimPlanningRejection` (rejected claims + mandatory-claim requirement), keeping the claim while re-organizing the chapter around a provable event — capped at `MAX_OUTLINE_REGEN_ATTEMPTS = 2` per chapter; once exhausted, the chapter stops for manual resolution with a `mandatory_beat_unproven` blocking report. Key-beat revocation is unaffected. Two chapter-level density signals feed routing from structured validation: `structured.zero-event-chapter` (warning; filtered draft events and expected events both empty) and `structured.mandatory-beat-unclaimed` (error; only under act-boundary high pressure when the chapter claims zero mandatory beats while current-act beats stay pending — the high-pressure claim invariant's validation-layer backstop). Independently of issue fingerprints, the cross-chapter zero-increment gate compares `diffMemorySnapshots(memoryBefore, applyEvents(memoryBefore, acceptedEvents))` (computed by `validate_chapter_structured` as `StructuredValidationResult.increment` via `src/story-memory/increment.ts`): a chapter with no character location/status, item holder/location/state, foreshadow plant/fulfill/extend, task, or plot-advance increment is zero-increment. The first consecutive zero-increment chapter lands a `structured.zero-increment-chapter` warning in the chapter report; at `zeroIncrementErrorThreshold` (default 2) consecutive ones, routing refuses finalize and force-regenerates the outline with a `ZeroProgressRejection` (last-N-chapters event counts) through the same outline-regeneration plumbing (shared `MAX_OUTLINE_REGEN_ATTEMPTS` cap), then stops with a `zero_progress_stall` blocking report. The streak counter lives in graph-state `consecutiveZeroIncrementChapters`, is updated at finalization, and resets on any increment.
- **Validation loop**: `validate_chapter_structured` verifies the structured event contract (evidence spans, foreshadow fulfillments, `STORY_FINAL_STATE` end-of-chapter declarations) before `validate_chapter_comprehensive` aggregates word-count, continuity, foreshadowing, and consistency checks. Final-state declarations that match the pre-chapter projection and appear among the chapter's own events are treated as "return to origin" and auto-complete the event stream (`source: 'final-state-completion'` events, recomputed every pass). Unauthorized (plan-external) `plot-advance` events are gated by the prose-level semantic verifier instead of hard rejection: verified ones are kept and consumed as real progress, unverified ones are dropped from `draftChapterEvents` with a warning (`structured.plot-advance-unauthorized-dropped`); other unauthorized event types remain hard errors. Because `STORY_EVENTS` is emitted before `CHAPTER_CONTENT`, an event's `@pN` evidence anchor is a prediction about not-yet-written paragraphs; when a claimed `plot-advance`/`foreshadow-fulfill` event fails semantic verification on its anchored paragraph, `src/graph/services/evidence-relocation.ts` searches the whole chapter (same strict criteria) for a paragraph that actually realizes the claim — found: the evidence pointer is corrected and the rejection dropped; not found: the rejection stands and reliably means the prose lacks the scene.
- **Foreshadow scheduling is advisory**: `selectForeshadowsForChapter` only proposes due/overdue candidates; the outline agent must adjudicate each into `fulfilledForeshadowIds` or `deferredForeshadowIds`, and the plan is validated against the outline's claims, never force-overridden. Severely overdue deferred foreshadows get bounded deadline extensions (`foreshadow-deadline-extend` events, max 2) at finalization; beyond the cap they are reported, not blocking. Exception: when the chapters left in an act cannot hold all pending required foreshadows (per-chapter fulfillment capacity), scheduling enters tight mode and marks the scheduled share 【强制回收】 — the outline is retried if they are deferred, and in strict mode (act-extension quota exhausted) a persistent refusal aborts the chapter with a manual-resolution error. Foreshadows without an `expectedFulfillChapter` only enter the candidate pool in the final act, sorted last; authors can also remove a foreshadow from the pool permanently via `waive-foreshadow` (`foreshadow-waive` event, `waivedIn` projection field).
- **Lifecycle semantics (B.1)**: `alive` is a controlled lifecycle attribute (`LIFECYCLE_ATTRIBUTES` in `src/types/story-memory.ts`, extensible); `character-status` events carry an optional typed `lifecycle: { attribute, value: boolean }` channel (also derived structurally from attribute=controlled-vocab + boolean literal), while free-text status remains for everything else. Shared semantics live in `src/story-memory/lifecycle.ts`. The projector tracks per-entity terminal flags: `alive=false` is terminal and monotone — ordinary status events can never flip it back; only an explicit `character-revival` event (with a plot-advance-style `@pN` evidence anchor) clears the flag. The validator enforces two deterministic invariants from the pre-chapter projection, applied sequentially over the chapter's accepted events: any event referencing a terminal entity (location/status/holder custody) → error `structured.entity-terminal-state-violation`; a second death event for an already-dead entity → error `structured.entity-terminal-duplicate`. Legacy checkpoints/memory without lifecycle fields are backfilled purely from structured event data by `backfillLifecycleProjection` (wired at the structured-validation node and finalization; free-text statuses are never guessed). `character-revival` counts as an increment for the zero-increment gate.
- **State authority hierarchy**: finalized chapter text > story-memory projection > outline structured declarations > `outline_inference` facts. `authorizeOutlineFacts` pre-authorized facts pass through a structural gate (no location/holder, known subject ids only, no projection conflicts) and persist via `canonicalFactsDelta`; they render as advisory hints and are superseded by chapter-extracted facts. Active canonicalFacts override memory location projections when rendering state.
- **Chapter-event fact harvesting (B.2)**: at finalization, `src/graph/services/finalization/fact-harvest.ts` derives canonicalFacts from the chapter's accepted event stream and corroborated final-state declarations — lifecycle facts (structured `lifecycle` marker on the fact), identity facts from `entity-register` events (B.3: `subject=entityId`, `value=displayName`), item custody (`holder`) changes, and declarations supported by the chapter's own events — tagged with the existing `'chapter_text'` source (semantics: harvested at chapter finalization). No prose parsing; only typed event/declaration data. Rendering (`prioritizeCanonicalFacts` in `src/graph/utils/reconciler/format.ts`, used by `formatStoryState` and the chapter contract's protected-facts section) replaces the old single 20-item window with priority lanes: (a) all terminal/lifecycle facts are never truncated; (b) facts for entities touched by the current chapter contract (`collectChapterContractEntityIds`: outline touched ids + expectedEvents entity ids) are pinned; (c) the rest render by recency up to `MAX_RENDERED_CANONICAL_FACTS = 40`. A death established in an early chapter therefore stays visible in every later writer/consistency prompt.
- **Entity registration (B.3)**: the `entity-register` event (`{ entityKind: 'character' | 'item', entityId, displayName }`; the introducing chapter is the event's `chapterIndex`) lets the writer/planner register a newly introduced named entity before referencing it — a creation event under the same discipline as `task-create.taskId` (fresh unique machine id, no known-id check). Registered entities enter the projector's entity tables (real id + readable name; placeholder `name===id` records get backfilled), so minor characters become location/status-trackable. `validatePlannedStoryEventAuthority` admits same-batch register-then-reference; references to unregistered ids keep the existing unknown-id error. Registration events are exempt from the expected/actual missing/unexpected diff (self-authorizing), count as increments (`entityRegistrations`) for the zero-increment gate, and feed `extractEstablishedCharacters` as an authoritative source (placeholder machine-id names skipped), reducing reliance on summary-JSON `characterFacts`. The planner prompt rule is "register first, then emit normally"; truly unnamed one-off walk-ons stay prose-only.
- **Structured story time (B.4)**: `storyState.storyTime` and `ChapterHandoff.endTime` are structured `StoryTime` objects (`{ era?, year?, month?, day?, dayFraction?, freeform? }`; `dayFraction` enum in `src/types/story-state.ts`, shared semantics in `src/utils/story-time.ts`). The summary agent contract emits these fields (`freeform` as the vague-narration fallback). Finalization runs two deterministic checks on this channel only (never on prose): monotonicity — a chapter end time earlier than the previous chapter's → error `structured.time-regression`; era consistency — an absolute date assertion (era+year) whose era differs from the running story era → error `structured.time-era-conflict`. Archive/document dates quoted inside the prose are item metadata, not story-time assertions; travel-duration feasibility stays in the LLM advisory lane by design. Legacy free-text `storyTime`/`endTime` values are normalized on read to `{ freeform: 原文 }` (`normalizeStoryTime`), so old checkpoints keep working without data edits.
- **Beat consumption corroboration (D)**: a mandatory beat is consumed only when its proven `plot-advance` event is corroborated by a structural trace (`src/story-memory/beat-corroboration.ts`, pure id/anchor matching — no NL): (a) a same-chapter state-class event (location/status/item/foreshadow-fulfill/task) bound to the proving event by shared `@pN` evidence anchor or shared subject (character/item entity id == the event's `plotId`, or a foreshadow whose registry `beatId` belongs to the beat), or (b) a final-state declaration corroborated by the chapter's own event stream (reusing `FINAL_STATE_EVENT_TYPES` / `finalStateEventValue` / `entityIdFromEvent` from the validator) and bound to the beat the same way. `validate_chapter_structured` fills `StructuredValidationResult.beatCorroborations`; routing turns an uncorroborated _claimed_ beat into a `beat_uncorroborated` error (`structured.beat-uncorroborated`) with one draft retry carrying beatCorroboration feedback ("the claimed outcome must leave a structural trace"), and on retry exhaustion converts it to `beat_unproven` (`structured.beat-uncorroborated-exhausted`) — the previous round counts as the unproven predecessor, so the existing revocation / high-pressure outline-regeneration paths apply immediately (high-pressure protection covers proven-but-uncorroborated mandatory beats via consumption-based `unprovenMandatoryBeatIds`). Unclaimed-but-verified uncorroborated beats are accepted as real progress with a warning only. At finalization `auditChapterBeatCorroboration` persists the audit record (`BeatMemory.corroboration: { status: 'consumed' | 'proven_uncorroborated', corroboratingEventIds, corroboratedByFinalState }`, monotone upgrade); act progress consumes only `consumed` beats — `proven_uncorroborated` beats stay pending, so the act-close review (`buildActBoundaryPendingIssue`) blocks act closure and names the uncorroborated beats (manual force-close remains the escape hatch). Key beats keep the single-verification standard. Pre-adoption consumed beats carry no audit record and are grandfathered as `consumed`.
- **State repair**: when a rewrite loop's remaining errors are all state-corruption issues (stale state records contradicting finalized chapters), routing enters the `repair_state` node (max `MAX_STATE_REPAIR_ATTEMPTS = 2` per chapter, `src/core/chapter-generation/routing/index.ts:24`): the LLM proposes structured state fixes that must pass strict structural validation (known entity ids, attribute enums, exact oldValue match, evidence chapter before the current one) before being written as canonicalFacts (`source: 'state_repair'`) and merged into storyState. Rejected proposals' reasons are stored in `session.stateRepairRejections` and fed back into the next attempt's prompt. If repair attempts are exhausted, routing falls back to the manual `request_rewrite` path.
- **Finalization**: `src/graph/services/finalization/chapter.ts` orchestrates finalization; `chapter-summary.ts` handles summary/state extraction, `chapter-events.ts` owns event filtering and completion issues, and `chapter-report.ts` builds reports. The flow verifies mandatory beats (stable IDs like `A{act}-M{index}`), audits mandatory-beat corroboration into `BeatMemory.corroboration` (see the beat-corroboration bullet), updates act progress (consumption requires corroboration for mandatory beats), writes chapter reports, and returns state updates without mutating the input graph state. Reports may include `modelUsage` with per-chapter calls, failures, transport retries, structured fallbacks, token usage, duration, and purpose counts.
- **Verified constraints**: runtime `verifiedConstraints` are structured objects. Render them to strings only at agent prompt boundaries; do not classify constraints by parsing natural-language prompt text.

## Agent Prompt Design Rules

All agent prompts (`src/agents/prompts/`) must follow these principles:

1. **Neutrality**: Prompts must express generic writing conventions, not rules tailored to a specific book, genre, or story. Do not hard-code genre-specific concepts (e.g., "previous life memory", "fate prophecy", "cultivation realms") into prompts.
2. **Abstraction over Example**: When forbidding patterns, state the abstract rule (e.g., "Do not end chapters with explicit chapter-end markers") rather than enumerating specific examples (e.g., "Do not use 'To be continued', '(End of Chapter)', 'Chapter X · Complete'").
3. **Configurable over Hard-coded**: Word-count requirements, genre conventions, and style rules must be read from `GenreSkill` / config, not baked into prompt strings.
4. **No Story Spoilers**: Agents must not reference future plot points, character arcs, or twists from the outline when checking current-chapter content.

## Code Architecture Rules

1. **No Story-Specific Hardcoding**: Never hardcode character names, item names, locations, or plot-specific keywords in source code (e.g., `desc.includes('孙悟空')`, `desc.includes('木之灵物')`). These are temporary patches that break when writing different stories. Such logic belongs in prompts or configuration, not in code.
2. **No Duplicate Filters**: Do not implement the same filtering/demotion logic in multiple places (e.g., both `write.ts` and `consistency.ts`). Centralize post-processing in the agent's `processOutput`/`parse` path.
3. **Fix Root Causes, Not Symptoms**: When an agent consistently misjudges a certain scenario, fix the agent's prompt or input context rather than adding hardcoded post-processing rules to downgrade specific outputs.
4. **No Natural-Language String Matching for Semantics (Critical)**: Runtime code must not use natural-language characters, keywords, phrases, fragments, regular expressions, n-gram overlap, LCS/fuzzy text similarity, or `includes`/`startsWith`/`endsWith`/`match` against prose to make semantic decisions. This is strictly forbidden even when the rule is generic rather than story-specific.
   - Forbidden uses include state/canonical fact updates, issue filtering or demotion, issue routing/classification, act or mandatory-beat verification, foreshadow filtering, outline-vs-state conflict decisions, pending-task resolution, paragraph/sentence repair targeting, and any other behavior that changes story state or control flow based on prose content.
   - Use structured data instead: stable IDs, enums, typed fields, explicit issue codes, subject/attribute/value records, evidence offsets/spans, chapter/paragraph/sentence indexes, structured model output with JSON schema, or author/config decisions.
   - Existing natural-language matching logic is technical debt to remove. Do not add new matching logic and do not extend existing matching logic while fixing bugs.
   - The only allowed string/regex matching is non-semantic parsing of machine-readable formats or explicit delimiters, such as JSON repair, Markdown/code fences, CLI flags, file names, checkpoint IDs, protocol names, and agent output section markers. If the input is story prose, issue prose, outline prose, summary prose, or prompt prose, matching its natural-language content is not allowed for decisions.
   - Enforced by `tests/smoke/no-prose-matching.test.ts`.

## Data Integrity Rules (Critical)

1. **Never modify `books/` directory directly**: The `books/` directory contains runtime-generated story data (meta.json, chapters, checkpoints). Direct modification causes data inconsistency, breaks reproducibility, and hides real code defects. All data changes must be driven by code logic or CLI commands.
2. **Code fixes over data patches**: When story data has errors (e.g., contradictory timeline, wrong character status), fix the code that generates or consumes the data (agents, runners, checkpointers) — never hand-edit the data files.
3. **Git does not track `books/`**: Since `books/` is `.gitignore`d, manual changes have no history and cannot be reverted. This makes debugging impossible.
4. **Checkpoint consistency**: Checkpoints, timeline snapshots, and meta.json reference each other. Modifying one without updating others creates orphaned references.

## Adding a New Agent

1. Create a class in `src/agents/{name}.ts` extending `BaseAgent` (`src/agents/base.ts`): implement `buildPrompt(state): Message[]` and `parse(content): AgentOutput`; shared prompt fragments live in `src/agents/prompts/fragments/`.
2. Add a thin node function under `src/graph/nodes/` or a focused service under `src/graph/services/` that instantiates and calls the agent through `src/graph/agent-factory.ts`.
3. Wire the node into `src/graph/novel.graph.ts`.
4. Add tests in `tests/agents/{name}.test.ts` with a mock `ModelProvider`.
5. Ensure the agent returns partial state updates that merge into `GraphState`.

## Model Provider Setup

Providers are configured via CLI: `npm start -- config set --provider <openai|anthropic> --api-key ... --model ... [--base-url ...]` (or `museflow config set ...` when installed). `minimax`/`local` are accepted as OpenAI-compatible shortcuts. Env fallbacks: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`.

The `ModelProvider` interface (`src/model/provider.ts`):

```ts
interface ModelProvider {
  chat(messages: Message[], temperature?: number, metadata?: ModelCallMetadata): Promise<string>
  chatStructured?<T>(
    messages: Message[],
    schema: JsonSchema,
    temperature?: number,
    metadata?: ModelCallMetadata
  ): Promise<T>
}
```

`src/model/registry.ts` picks `OpenAICompatibleProvider` or `AnthropicCompatibleProvider` from config, falls back to a JSON-schema prompt + `extractJsonBlock`/`repairMalformedJson` when native structured output is absent or rejected with HTTP 400/422, and optionally wraps everything in `DebugModelProvider` when debug is enabled. `src/model/telemetry.ts` records logical calls, failures, transport retries, fallback usage, token counts, duration, and chapter/purpose metadata; `src/graph/nodes/finalization.ts` attaches the chapter summary to `chapterReport.modelUsage`.
