# CLI 伏笔边界压力展示设计

## 背景

章节状态区目前只展示当前幕的章节位置和 mandatory beat 消费进度。幕边界调整还会受到 required 伏笔约束影响，因此即使节拍已经全部消费，系统仍可能因到达当前幕回收窗口的伏笔而自动延长幕边界。CLI 没有展示这部分结构化状态，用户无法从写作前的状态区理解扩幕原因。

## 目标

- 在写作前展示当前幕的 required 伏笔边界压力。
- 展示阻断伏笔总数、稳定 ID 和预计回收章节。
- 让 `write`、`rewrite`、`continue` 与 `status` 使用同一查询规则。
- 查询只依赖结构化字段，不解析伏笔或剧情自然语言。

## 非目标

- 不修改伏笔调度、幕边界调整或章节定稿策略。
- 不改变 required 伏笔的期限或兑现状态。
- 不直接修改任何 `books/` 运行数据。
- 不展示尚未进入当前幕边界回收范围的远期伏笔。

## 方案

### 共享结构化查询

在伏笔策略模块提供面向幕边界展示的查询。输入为 `StoryMemory` 和当前幕结束章节，输出保持预计回收顺序的结构化伏笔列表。

列表只包含同时满足以下条件的条目：

- `required` 为 true；
- `fulfilledIn` 为 null；
- `expectedFulfillChapter` 是有效期限；
- `expectedFulfillChapter` 不晚于当前幕结束章节。

查询复用现有 required 伏笔调度规则，避免 CLI 复制另一套过滤逻辑。返回条目保留 ID 和预计回收章节，CLI 不读取或匹配伏笔文本。

### CLI 输出

`printActProgress` 在节拍信息之后输出：

```text
  伏笔边界压力: 3 个 required 伏笔待回收
  待回收伏笔:
    1. fs-example-a（预计第 35 章）
    2. fs-example-b（预计第 36 章）
    3. fs-example-c（预计第 37 章）
```

没有阻断伏笔时输出：

```text
  伏笔边界压力: 0
```

`status` 的故事弧线区域输出同样的信息和条目，仅缩进适配现有 status 格式。旧检查点没有 `storyMemory` 时按无可用压力数据处理，安全输出 0。

### 数据流

1. CLI 从检查点取得 `ReducedGraphState`。
2. CLI 根据目标章节定位当前幕。
3. 共享查询使用 `state.storyMemory` 和 `act.endChapter` 计算边界伏笔列表。
4. 展示层格式化总数、ID 和预计回收章节。

整个流程只读，不产生状态事件，也不调整幕边界。

## 测试

- 伏笔策略单元测试：仅返回 required、未兑现、期限有效且不晚于边界的伏笔，并保持既有调度顺序。
- 章节状态测试：`printActProgress` 展示数量、ID、预计章节；无 `storyMemory` 时显示 0。
- status 测试：故事弧线区域展示相同的边界压力。
- 回归验证：运行相关 Vitest、完整测试、类型检查和构建。

## 兼容性与风险

该变更只增加 CLI 输出，不改变持久化格式或业务控制流。主要风险是展示规则与实际扩幕规则发生漂移；通过复用伏笔策略模块的结构化查询而不是在两个 formatter 内各自过滤来规避。
