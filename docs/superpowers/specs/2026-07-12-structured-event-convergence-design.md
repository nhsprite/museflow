# Structured Event Contract and Rewrite Convergence Design

## Problem

Chapter generation currently has two incompatible structured-event boundaries:

- `ChapterPlannerAgent` accepts `expectedEvents` after checking only `id`, `type`, and
  `chapterIndex`. Event-specific fields are not validated.
- `ChapterAgent` emits a text `STORY_EVENTS` block that is parsed into the strict
  `StoryEvent` union. Its item-location syntax records a holder, while a planner can emit
  only a location; its item-state syntax records `attribute` and `value`, while a planner
  can emit an untyped `state` field.

`validateChapterEvents` compares the resulting typed fields exactly. A malformed plan can
therefore produce a permanent missing/unexpected event pair even when the prose describes
the intended action.

The routing layer makes that validation failure non-terminating. Structured blockers return
`fix` before the normal rewrite policy runs. The fix paths change staged prose but do not
replace `draftChapterEvents`, and the early return does not increment
`errorRewriteAttempts` or update fingerprint history. LangGraph eventually stops the cycle
only because `recursionLimit` is exhausted.

## Goals

- Make one discriminated runtime contract authoritative for every `StoryEvent` producer and
  consumer.
- Preserve compatible legacy checkpoints without editing files under `books/`.
- Replan legacy chapter plans that cannot be normalized without guessing semantics.
- Ensure structured validation retries regenerate both prose and structured events.
- Guarantee that repeated structured failures stop through the existing blocking-report
  path before the graph recursion limit.
- Replace stale structured issues on every validation round.

## Non-Goals

- Do not infer story semantics from prose or natural-language fragments.
- Do not weaken deterministic event comparison.
- Do not migrate or hand-edit runtime story data.
- Do not redesign StoryMemory projection or finalization.

## Decision

### 1. Shared event contract

Add a focused story-event contract module that validates an unknown value as one member of
the `StoryEvent` discriminated union. Validation is based only on typed fields:

- common fields: `id`, `type`, `chapterIndex`, and `source`;
- character location: `characterId`, `locationId`;
- character status: `characterId`, `attribute`, `value`;
- item location: `itemId`, `holderId`, `locationId`;
- item state: `itemId`, `attribute`, `value`;
- plot, foreshadow, and task events: their existing typed identifiers and required values.

The module returns a structured success/failure result rather than casting partially checked
objects to `StoryEvent`. New planner output must pass strict validation.

### 2. Legacy normalization

At the chapter-plan consumption boundary, normalize legacy events only when the conversion
is mechanical and unambiguous:

- missing `source` becomes `chapter`;
- the authoritative current `chapterIndex` replaces a stored display index;
- an item-location event with exactly one valid location target receives
  `holderId: null`;
- an item-location event with exactly one valid holder target receives
  `locationId: null`.

Legacy item-state objects using only `state`, or item-location objects whose target cannot be
classified as a stable holder/location ID, are not translated through prose heuristics. The
current `ChapterPlan` is invalidated and regenerated by the planner. This preserves old data
when safe and avoids inventing an `attribute` or entity identity.

Normalization happens in memory during the graph run. No checkpoint or `meta.json` file is
modified directly.

### 3. Explicit item-location output format

Change the `STORY_EVENTS` contract for item locations to carry both typed dimensions:

```text
- item-location: <itemId> / holder=<holderId|none> / location=<locationId|none> @pN
```

The parser accepts this canonical format and returns explicit nullable fields. The previous
single-target format remains readable for legacy model output only when the target has a
stable ID prefix that makes holder versus location unambiguous. Otherwise the line is
rejected instead of turning free-form prose into an entity ID.

The chapter prompt embeds `chapterPlan.expectedEvents` and requires the writer to preserve
their typed fields exactly. Event instance IDs remain runtime-generated because event
matching is based on typed payload identity, not event-log identity.

### 4. Structured retry routing

Convert fresh structured validation failures to ordinary `Issue` objects before applying the
rewrite policy. Structured issue types use `retryStrategy: draft`, because correcting them
requires a new `STORY_EVENTS` block and therefore a fresh `draftChapterEvents` value.

Remove the structured-validation early return. The combined current issues flow through the
existing policy, which:

- increments `errorRewriteAttempts`;
- records issue fingerprints;
- chooses a full draft instead of the paragraph FixAgent;
- stops with `request_rewrite` after the configured maximum or a stalled fingerprint set.

If validation reports that the plan itself is malformed, the draft decision discards the
plan so `expandOutlineForChapter` invokes the planner again. A valid plan with missing or
unexpected draft events is retained and the chapter is redrafted against it.

### 5. Current-round issue ownership

Define the structured issue types as an explicit enum-backed set. Before adding issues from
the latest `StructuredValidationResult`, remove earlier issues of those types. Other current
issues remain subject to the existing issue policy.

This replacement is based on structured issue codes, not descriptions, and prevents new
random issue IDs from accumulating across validation rounds.

## Data Flow

1. The planner returns a candidate `ChapterPlan`.
2. The plan boundary normalizes compatible legacy events and strictly validates every event.
3. An invalid plan is retried during planning or discarded when resumed from a checkpoint.
4. The chapter writer receives canonical expected events and emits canonical
   `STORY_EVENTS` plus prose.
5. `ChapterAgent` parses the event block into fresh `draftChapterEvents`.
6. Structured validation compares canonical expected and actual typed fields.
7. Blocking results replace the previous round's structured issues.
8. Routing redrafts and increments the normal error budget, or requests manual rewrite when
   the budget/stall condition is reached.
9. Only a passing structured result can proceed to finalization and StoryMemory projection.

## Error Handling

- Invalid new planner events cause a bounded planner retry with an explicit structured-field
  error.
- Invalid legacy plans cause in-memory plan invalidation and replanning.
- Unparseable writer event lines are omitted, producing a deterministic missing-event issue
  that enters the bounded draft retry path.
- Repeated failures produce the existing structured blocking report rather than
  `GRAPH_RECURSION_LIMIT`.
- Raising `recursionLimit` is not part of the solution.

## Testing

Use red-green TDD for each behavior:

1. Contract tests reject incomplete item-location and item-state events.
2. Contract tests accept every valid `StoryEvent` variant.
3. Legacy normalization fills nullable item-location fields and rejects ambiguous or
   `state`-only events.
4. Planner tests prove malformed subtype fields no longer enter a `ChapterPlan` silently.
5. Parser tests cover the canonical item-location syntax and legacy-safe fallback.
6. Validator tests prove canonical planned and written item events match.
7. Routing tests prove structured blockers choose `draft`, increment
   `errorRewriteAttempts`, replace stale structured issues, and request rewrite at the limit.
8. Graph-level regression coverage proves a redraft replaces `draftChapterEvents` and the
   loop terminates without invoking the FixAgent repeatedly.

Verification consists of focused tests, the full Vitest suite, `npm run typecheck`, and
`npm run build`.

## Compatibility and Rollout

- Checkpoint schema remains unchanged.
- Compatible legacy events are normalized at runtime.
- Incompatible current plans are regenerated only for the chapter being written.
- Existing finalized StoryMemory events are not rewritten.
- No direct changes are made to `books/`.
